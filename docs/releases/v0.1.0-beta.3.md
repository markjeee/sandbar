# Sandbar v0.1.0-beta.3

This prerelease targets Linux amd64 and macOS arm64. Ubuntu 24.04 is the Linux acceptance target.
Install Caddy v2.11.7 or a later v2 release separately.
Linux uses apt Caddy, systemd, Polkit, and sudo. macOS uses native Homebrew Caddy.
macOS executables are unsigned and unnotarized. Intel Macs and Windows are not supported.

## Install and upgrade

```sh
curl -fsSL https://github.com/markjeee/sandbar/releases/download/v0.1.0-beta.3/install.sh | sh
```

Packages need no Go runtime or compiler. The installer verifies the matching archive with SHA-256 before atomic replacement.
Linux defaults to `~/.local/bin/sandbar`. Add `~/.local/bin` to PATH.
macOS installs a regular executable at `/usr/local/bin/sandbar` and requests administrator access only when final publication needs it.
Use `--bin-dir <directory>` for another destination.
Executable installation does not install Caddy, run setup, start services, edit shell profiles, or change trust.
Preview and apply setup separately.

On macOS, run as your normal user:

```sh
sandbar setup --check --http-port 80 --https-port 443
sandbar setup --http-port 80 --https-port 443
```

On Linux:

```sh
sudo "$HOME/.local/bin/sandbar" setup --check --user "$USER"
sudo "$HOME/.local/bin/sandbar" setup --user "$USER" --replace-default-site
```

`--replace-default-site` authorizes only Caddy's recognized stock welcome site. Custom sites remain protected.
Linux grants access to all Caddy routes and files Caddy can read. Grant access only to users who may administer Caddy.
Log out and back in after Linux group changes. A new terminal pane does not refresh membership.
Fresh CAs need a separate `sandbar trust` request as your normal user.
Unchanged CA identity retains existing trust. Setup does not import or remove trust.

Setup upgrades installed configuration to version 3 and saves a stable machine name.
It preserves routes, configured ports, CA identity, and unrelated supported Caddy content.
Existing macOS ports remain saved when options are omitted. Use explicit flags above to move to 80/443.
Keep the reported setup backup. Older binaries cannot read version 3 configuration.
Rollback restores matched source, generated files, setup files, and service state before using the older executable.
Keep original CA storage and trust. Private development upgrades save matched version 1 or version 2 source and Caddyfile backups.
Beta.1 users still need explicit private-router migration before installed service cutover.
Follow [installation and recovery](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.3/docs/install.md) and [source upgrades](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.3/docs/reference.md#upgrade-existing-source).

## macOS launchd service

Sandbar manages one current-user LaunchAgent, `local.sandbar.caddy`, after explicit setup.
Launchd opens loopback TCP 80, TCP 443, and UDP 443. Caddy inherits sockets and runs as your user.
HTTP/1.1, HTTP/2, and HTTP/3 share the configured HTTPS port. Custom ports remain supported.
Homebrew supplies Caddy. Do not run its user service alongside Sandbar's job.
Start registers login startup. Stop unloads the job and releases its sockets. Route changes apply without restarting Caddy.
The user service does not run before login. Actual startup after logout/login remains deferred in acceptance.
Registration, start/stop checks, and inherited-socket tests do not establish that deferred result.
Sandbar uses Caddy's original public root certificate without a redundant macOS state copy.

## Teleport

Machine `work` automatically serves `app.sandbar-work.localhost` alongside `app.sandbar.localhost`.
On work, the machine URL routes directly to its backend without SSH or an HTTP redirect.
Both peers need beta.3 or another Teleport-capable Sandbar, completed setup, and prepared remote Caddy/apps.
Matching browser-facing HTTPS ports let both machines use the same full URL.
Use an existing SSH agent with its keys loaded. Sandbar keeps dedicated SSH configuration and known-host files.
It does not manage keys or forward the agent. OpenSSH verifies remote host keys normally.

| Command | Result |
| --- | --- |
| `sandbar teleport register work` | Save the destination, then connect. |
| `sandbar teleport connect work` | Connect or reuse its connection. |
| `sandbar teleport disconnect work` | Disconnect while keeping registration. |
| `sandbar teleport ls` | Show destinations and observed SSH state. |
| `sandbar teleport rm work` | Disconnect and remove the destination and proxy trust. |
| `sandbar teleport info --json` | Show public peer metadata. |

After registration, open `https://app.sandbar-work.localhost` on the connecting machine.
Registration configures only the connecting machine. It obtains the remote root over verified SSH for proxy transport verification.
Browsers use the connecting machine's CA. Registration does not import the remote CA into browser or system trust.
A failed connect retains registration. Connect explicitly after correcting the connection.
Connections stay open until disconnected. Boot, login, and Caddy startup do not connect automatically.
An unavailable registered connection returns ordinary HTTP 502. Unknown destinations follow normal Caddy behavior.
Apps must accept machine URLs in allowed hosts, CSRF origins, redirects, cookies, and login settings.
Sandbar does not rewrite app URLs or responses. See [Teleport](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.3/docs/teleport.md).

## Verification and limits

Native checks cover Linux amd64 and macOS arm64. Disposable Linux service CI remains separate from personal installations.
Development candidates without authored notes remain identified as unpublished local packages.
Public installation checks use temporary destinations without setup, trust changes, or installed service changes.
See [development and acceptance](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.3/docs/development.md) for the check layers and deferred manual acceptance.

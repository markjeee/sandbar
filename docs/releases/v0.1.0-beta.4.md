# Sandbar v0.1.0-beta.4

This prerelease adds configuration inspection, diagnostics, and installed cleanup to beta.3's Teleport and macOS support.
It targets Linux amd64 with apt Caddy, systemd, Polkit, and sudo, or macOS arm64 with native Homebrew Caddy.
Install Caddy v2.11.7 or a later v2 release separately. Ubuntu 24.04 is the Linux acceptance target.
macOS packages are unsigned and unnotarized. Intel Macs and Windows are not supported.

## Install and upgrade

```sh
curl -fsSL https://github.com/markjeee/sandbar/releases/download/v0.1.0-beta.4/install.sh | sh
```

Packages need no compiler or Go runtime. The installer checks the matching archive's SHA-256 before atomic executable replacement.
Checksums share the HTTPS release source. They check transfer integrity, not an independent signature.
Linux defaults to `~/.local/bin/sandbar`. Add `~/.local/bin` to PATH.
macOS defaults to the regular executable `/usr/local/bin/sandbar`. Use `--bin-dir <directory>` for another destination.
The installer requests macOS administrator access only when final executable publication needs it.
It does not install Caddy, run setup, start services, edit shell profiles, or change trust.

Existing beta.3 installations need only executable replacement. No new schema migration or setup is required for this upgrade.
Version 3 configuration, machine identity, routes, CA, Teleport registrations, services, and trust remain unchanged.
Setup, trust changes, connection changes, and uninstall remain separate explicit actions.

Fresh installations require separate setup. Run macOS setup as your normal user:

```sh
sandbar setup --check --http-port 80 --https-port 443
sandbar setup --http-port 80 --https-port 443
```

On Linux:

```sh
sudo "$HOME/.local/bin/sandbar" setup --check --user "$USER"
sudo "$HOME/.local/bin/sandbar" setup --user "$USER" --replace-default-site
```

`--replace-default-site` authorizes only Caddy's recognized stock welcome site. Custom sites remain protected.
Linux grants access to all Caddy routes and files Caddy can read. Grant access only to users who may administer Caddy.
Log out and back in after Linux group changes. A new terminal pane does not refresh membership.
Fresh CAs need a separate `sandbar trust` request as your normal user. Unchanged CA identity retains existing trust.

For beta.2 or older source, explicit setup upgrades configuration to version 3 and preserves supported routes, ports, and CA identity.
Keep the reported setup backup. Older binaries cannot read version 3 configuration.
Rollback requires matched source, generated configuration, setup files, and service state before using the older executable.
Keep original CA storage and trust. Private development upgrades require their matched source and generated Caddyfile backups.
Beta.1 users still need explicit private-router migration before service cutover.
Follow [installation and recovery](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.4/docs/install.md) for earlier upgrades and rollback.

## Inspect and diagnose

| Command | Result |
| --- | --- |
| `sandbar config --path` | Print the selected absolute source path, even before setup. |
| `sandbar config --print` | Print exact source bytes, including readable invalid JSON. |
| `sandbar status` | Inspect local service, routes, pending state, and current-user Teleport connections. |
| `sandbar doctor` | Diagnose configuration, listeners, resolution, HTTPS, trust, and Teleport transport separately. |

Inspection does not repair state, change permissions, start services, request trust, or connect SSH destinations.
HTTPS probes can still cause server logs or certificate issuance. Results are snapshots and can become stale.
Disconnected or unknown Teleport state alone does not make status or doctor fail. Disconnected destinations show an explicit connect command.
Connected SSH does not prove forwarded HTTPS or app health. Failed local checks and attempted transport checks can still return nonzero.
System verification does not prove browser trust. See [diagnostic results](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.4/docs/reference.md#inspect-and-diagnose).

## Uninstall installed Sandbar

| Command | Result |
| --- | --- |
| `sandbar uninstall --check` | Preview installed cleanup without changing files, services, connections, or trust. |
| `sandbar uninstall --yes` | Confirm cleanup of owned installed state while retaining the CLI. |

Run as your normal user without `--home` or `SANDBAR_HOME`. Bare uninstall makes no changes.
Linux requests ordinary sudo authorization for protected inspection and system cleanup, including inspection during preview.
Trust and SSH actions use the caller's environment. macOS unloads the current-user Sandbar LaunchAgent and releases its sockets.

Uninstall refuses before mutation if unrelated sites or listeners remain in the selected Caddy service.
It verifies ownership and stops the selected service before deleting runtime files and certificates.
Successful cleanup removes owned routes, machine identity, registrations, SSH files, runtime state, setup backups, integration, and selected Sandbar CA material.
It keeps the CLI, Caddy package, packaged unit, Caddy account, shared logs, unrelated authorities and files, and private development homes.
Backends, personal SSH files, keys, agents, and remote machines remain unchanged.

Owned connections close before exact-root untrust. Untrust failure preserves configuration, all CA material, public copies, and setup backups.
Some trust stores might already have changed. Disconnected connections remain disconnected.
Partial cleanup reports completed actions, the failure, and retained paths. No automatic reconnect, retrust, restart, or file restoration runs.
Caddy untrust success does not prove removal of manual browser imports or other users' trust.
Record the root fingerprint and remove manual imports that require its file before confirming cleanup.
Fresh setup creates a new CA and requires deliberate trust and peer registration updates.
Read [removal and recovery](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.4/docs/install.md#uninstall-installed-sandbar) before confirmation.

## Existing Teleport and macOS behavior

Both Teleport peers still need beta.3 or another Teleport-capable Sandbar, completed setup, and prepared remote Caddy and apps.
Registration configures the connecting machine, saves the destination, then calls connect using the existing SSH agent.
Machine-qualified URLs route locally on their own machine. Remote apps must accept those URLs.
Browsers use the connecting machine's CA. Registration stores the remote CA only for that destination's proxy transport verification.
An unavailable registered connection returns ordinary HTTP 502. Reconnect explicitly. No automatic connection or reconnect daemon is added.

macOS still uses one current-user LaunchAgent with loopback HTTP TCP and HTTPS TCP/UDP sockets.
Caddy runs as the user. The service does not run before login. Homebrew supplies Caddy but must not run a competing service job.
Existing configured ports remain unchanged. Setup is required to change the saved socket plan.

## Verification and limits

Native shared checks, CI, package verification, and public installation checks are separate release gates.
Public installation checks use temporary destinations without setup, trust changes, live uninstall, or installed executable replacement.
Ordinary Linux service CI does not establish privileged uninstall acceptance. The disposable Ubuntu uninstall acceptance remains deferred.
Actual macOS startup after logout/login remains deferred. Registration, start/stop, and inherited-socket checks do not establish that result.
Browser trust and manual import removal require separate checks. Package verification does not prove them.
Candidate versions without authored notes remain unpublished local packages.
See [development and acceptance](https://github.com/markjeee/sandbar/blob/v0.1.0-beta.4/docs/development.md) for check boundaries.
